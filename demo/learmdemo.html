method

Seven questions before you call something a fix.

The point is not to label patterns “good” or “bad.” The point is to earn the classification from evidence.

Observable

What looks successful or broken right now? Tests, latency, scan, dashboard, phenotype, price?

Requirement + authority

What must actually be true, and which state is authoritative? A proxy is not the requirement.

Persistent impairment

What remains wrong even if the observable looks normal? If you cannot name it, say unresolved.

Effect vector

Did the intervention repair impairment, reduce incoming burden, create capacity, change the requirement, or compensate?

Recipient + finite stock

If burden moved, who receives it? If compensation is finite, name the stock and its bound.

Joint executability

Every required condition must hold inside one plan; alternative complete plans compete between plans.

Second challenge + uncertainty

Remove support or perturb again. If evidence still cannot identify the state, report UNRESOLVED.

Future options

Ask not only whether today works, but which complete future responses remain executable afterward.

Core firewall: a retry is not automatically displacement, a refactor is not automatically restoration, a protein is not automatically repair, and a drug is not automatically masking. Classify by measured state effect.

time

The interval can change the thing that later needs repair.

Functional failure and operational termination are different clocks. The interval between them can be productive or destructive depending on what gets built inside it.

T_F

Required function is lost. A fallback keeps operation alive.

+1

New callers and automation begin depending on the fallback.

+2

State, contracts and operational assumptions accumulate around it.

+3

The workaround becomes endogenous infrastructure rather than temporary support.

T_O / transition

Repair target has changed. Fix + migration + obligation preservation are now jointly required.

Productive purchased time

Fallback buys an interval that is converted into repair, capacity creation, requirement reduction or an orderly structural transition.

Compounding purchased time

Fallback buys an interval in which more dependencies, liabilities or adaptation accumulate around the unresolved state, contracting future options.

AI reasoning

Success is not explanation.

If two agents score the same, what machinery did each need to stay successful?

Track retries, tools, human rescue, context, judge intervention and future task options. A model should also refuse to infer hidden capacity when the evidence does not identify it.

Biology

Match the outcome. Challenge again.

Two tissues look equally recovered. Are they equally capable?

Withdraw support, apply the same second perturbation, measure persistent impairment, compensatory resource use, recipient burden and recovery trajectory rather than only today's phenotype.

Cancer

Competing future option sets.

Which therapy preserves the patient's options while shrinking the tumor's escape options?

Equal tumor shrinkage can leave radically different residual clone diversity, host reserve and future treatment space. This suggests an adversarial executability extension worth testing, not yet adding to the kernel.

negative control

Compensation is not automatically bad.

A framework that calls every fallback unhealthy is useless. The right answer can be “keep the compensation.”

Legitimate buffering

A bounded queue absorbs a temporary burst, the arrival rate returns below service capacity, the queue drains, deadlines are met, no new dependency becomes permanently load-bearing, and future options are preserved.

Classification: appropriate architecture, not evidence of hidden decline.

Masking a sustained mismatch

The same queue keeps the process alive while arrivals remain permanently above sustainable throughput. Waiting, rejection or retries move upstream and the requirement remains unmet.

Classification: continuity may be preserved, but the underlying throughput mismatch remains.

AI use

Compact DST-aware review prompt.

This prompt forces mechanism-first reasoning while preserving uncertainty and negative controls.

DST / executability engineering review
Before proposing a fix:

1. OBSERVABLE — What looks successful or broken right now?
2. REQUIREMENT — What must actually be true for the system to count as functioning?
3. AUTHORITY — Which state is authoritative? Do not promote a proxy, cache, index, metric, test or UI into truth without justification.
4. PERSISTENT IMPAIRMENT — What would remain wrong even if the observable looked normal?
5. EFFECT VECTOR — For each intervention, separate:
   • reduction of incoming burden
   • genuine reduction of existing impairment
   • durable capacity creation
   • real requirement reduction
   • transfer / compensation through another route, recipient or finite resource
6. RECIPIENT + COST — If burden moved, where did it go? If compensation is finite, name the stock, rate limit, deadline or recipient capacity.
7. JOINT EXECUTABILITY — A proposed future is valid only if every required condition can hold together. AND inside a plan; OR between complete plans.
8. SECOND CHALLENGE — Remove the support, increase load, repeat the perturbation, delay a dependency, or exhaust the relevant resource. What result distinguishes repair from continuity?
9. FUTURE OPTIONS — Which complete responses remain executable after the intervention? Do not treat option count alone as option quality.
10. UNCERTAINTY — If the evidence does not identify the hidden state or intervention class, output UNRESOLVED and state what evidence would resolve it.

Required output:
Observable · requirement · authoritative state · persistent impairment · intervention effect · recipient/resource · executable plans · second challenge · future option change · falsifier / unresolved evidence.
